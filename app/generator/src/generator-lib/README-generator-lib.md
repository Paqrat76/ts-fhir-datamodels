# Generator Library (`generator-lib`) Developer Documentation

## Purpose and Scope

`app/generator/src/generator-lib` contains the generator runtime internals used to transform FHIR package artifacts
into TypeScript model source code. This documentation is implementation-focused for maintainers.

This directory is responsible for:

- Defining typed interfaces for loaded FHIR artifacts (`StructureDefinition`, `ValueSet`, `CodeSystem`)
- Normalizing FHIR datatype names into generated class naming conventions
- Defining generator contracts (`FhirPackage`, `GeneratedContent`, etc.)
- Building and configuring package-loader runtime dependencies
- Providing template support for class/method code generation patterns

Design and behavior in this document intentionally align with project-wide `dev-docs/*.md` references (see
"Related Documentation").

## Runtime Integration and Data Flow

Primary callers:

- `app/generator/src/typescript-datamodel-generator.ts`
- `app/generator/src/generator-app.ts`

High-level flow:

1. Caller builds a `FhirPackage` (typically via `getFhirPackage()`).
2. `generatorPackageLoader()` wires `BasePackageLoader` with:
   - SQLJS package DB (`createSQLJSPackageDB`)
   - disk cache at `<cacheRootPath>/.fhir/packages`
   - default registry client
   - `build.fhir.org` current-build client
3. Generator logic reads FHIR artifacts through `fhir-artifact-interfaces.ts` types.
4. Template support modules generate TypeScript source text using datatype rules from `fhir-data-type.ts`.
5. `GeneratorApp.writeDataModelsToDisk()` routes generated files by `FhirType` (`code-systems`, `complex-types`,
   `resources`) and writes `index.ts` barrel exports.

## File Responsibilities

### `ts-datamodel-generator-helpers.ts`

- Defines runtime contracts:
  - `FhirRelease` (`'R4' | 'R4B' | 'R5'`)
  - `FhirType` (`'CodeSystem' | 'ComplexType' | 'Resource'`)
  - `FhirPackage`, `GeneratedContent`, `GeneratedComplexTypeContent`, `GeneratorPackageLoaderOptions`
- `getFhirPackage()` maps release to defaults:
  - `R4` => `hl7.fhir.r4.core#4.0.1`
  - `R4B` => `hl7.fhir.r4b.core#4.3.0`
  - `R5` => `hl7.fhir.r5.core#5.0.0`
  - default `baseOutputPath`: `src`
  - default `pkgLoaderCacheRootPath`: `os.homedir()`
- `generatorPackageLoader()` is the single wiring point for package-loader initialization.
- `generateLicenseContent()` and `generateModuleContent()` enforce generated-file header consistency.
- `generatorLogger()` standardizes generator log format.

### `fhir-data-type.ts`

- Exposes canonical datatype sets:
  - `OPEN_DATA_TYPES`
  - `OPEN_DATA_TYPE_KEY_NAMES`
  - `DATA_TYPES`
  - `FhirDataType`
- Exposes `DATA_TYPE_MAPPINGS` with naming rule:
  - lowerCamelCase primitives -> `UpperFirst(name) + 'Type'` (example: `string` -> `StringType`)
  - PascalCase complex/special types remain unchanged
- Mirrors core-library datatype behavior without introducing direct generator dependency on `@paq-ts-fhir/fhir-core`.

### `fhir-artifact-interfaces.ts`

- Stable interface boundary for package-loader artifacts.
- Cloned/curated from `@types/fhir` (`r5.d.ts`) and trimmed to needed resource/type surface.
- Focuses on structures needed for generation of `StructureDefinition`, `ValueSet`, `CodeSystem` workflows.

Maintenance guidance:

- Treat as a stable boundary; avoid broad re-sync edits.
- Apply only targeted changes required by parsing/generation behavior.

### `templates/`

- Contains Handlebars templates and companion transformer modules.
- `partials/` contains reusable field/method pattern snippets.
- Variable mapping conventions are documented in `templates/README-Templates.md`.

- `dev-docs/fhir-data-model-design.md`

## Key Contracts and Invariants

1. `GeneratedContent.fhirType` must be one of (`CodeSystem`, `ComplexType`, `Resource`) so output routing remains valid.
2. `GeneratedContent.filename` is used for both file output and barrel exports; keep stable, extension-free export names.
3. `DATA_TYPE_MAPPINGS` must stay consistent with template import/class naming expectations.
4. `getFhirPackage()` defaults are consumed by app/tests; package name/version changes require deliberate release validation.
5. Header helpers (`generateLicenseContent()`, `generateModuleContent()`) are consistency contracts for generated files.

## Extension Playbook

### Add a new FHIR release

1. Extend `FhirRelease` and `getFhirPackage()` mapping in `ts-datamodel-generator-helpers.ts`.
2. Verify release package metadata and cache/runtime loading behavior.
3. Follow package-level onboarding and validation checklist in `dev-docs/add-fhir-release-pkg.md`.
4. If primitive set changed for the new release, update `@paq-ts-fhir/fhir-core` first (per `add-fhir-release-pkg.md`).

### Change datatype behavior

1. Update type lists/mappings in `fhir-data-type.ts`.
2. Confirm primitive vs. complex naming emits expected generated class names.
3. Revalidate template imports/usages and inheritance consistency with `dev-docs/data-model-framework.md`.

### Update FHIR interfaces

1. Confirm change is required by artifact parsing or generation behavior.
2. Apply minimal interface surface edits in `fhir-artifact-interfaces.ts`.
3. Re-run generator tests covering resource, complex type, and code system generation paths.

### Modify templates

1. Prefer reusable updates under `templates/partials` for shared patterns.
2. Keep `*.hbs` and corresponding `*-hbs.ts` support logic synchronized.
3. Verify generated output still satisfies:
   - Element cardinality/type method patterns (`dev-docs/fhir-data-model-design.md`)
   - Serialization assumptions (`dev-docs/design-notes.md`)
